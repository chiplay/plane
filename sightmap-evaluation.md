# Sightmap evaluation against Plane

Skeptical outside-engineer evaluation. Nothing was taken on faith: every claim below was exercised against a live app.

**What was evaluated**

| Item          | Version                                                                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Spec/CLI repo | github.com/sightmap/sightmap @ `428ff79944d431eff06c68b9202d9f405cd5fb9b` (2026-07-30)                                                                       |
| CLI           | `@sightmap/sightmap` **0.16.1** (npm, published 2026-07-30T14:03Z), spec stream 1                                                                            |
| Test bed      | Plane (`chiplay/plane` @ `a8e53b6`) — React Router v7 SPA (Vite) on :3000, Django API on :8000, run natively in a rootful Linux container (no Docker daemon) |
| App data      | Seeded workspace `falcon`, project FALCON, 8 work items across 5 states, 1 cycle, 1 module                                                                   |

**Verdict in one paragraph.** The core loop is real and mostly works as documented: the coverage model, selector probing, the novelty-gated capture sets, the devtools collector, and the loud interaction failures are solid engineering, and the A/B test shows the corpus genuinely pays for itself on observation and navigation tasks (nav task: 18→6 commands, 4→1 wrong turns). But the project currently fails its own conformance bar — the reference CLI and the published JSON schema disagree in **both directions** — the marketing page's hero terminal runs a command that does not exist, the documented Linux install flow is broken (`browser install` installs a Chrome that `browser start` cannot find), and several failure modes the format invites (stale maps in plain snapshots, two corpora in scope, wrong memory entries) are silent exactly where an agent would be misled.

## Phase 2 — Install and first run

Followed published instructions only (`npm install -g @sightmap/sightmap`, `sightmap skills install`, `sightmap browser install`).

- npm install → working CLI: **2.5 s**. Skills install: <1 s. Chrome for Testing download: **9.6 s**.
- **Documentation/implementation defect (Linux):** `sightmap browser start` failed with `chrome: no Chrome binary found in PATH on Linux` _after_ `browser install` had succeeded. Root cause (source-confirmed): `FindChrome()` (go/browser/launcher.go:151-158) only scans PATH for `google-chrome`/`chromium` names on Linux; the sightmap-managed `~/.sightmap/browsers/` install is consulted **only on macOS** (launcher.go:120-123). The docs present `browser install` as the remedy for exactly this error. Workaround required: symlink the CfT binary onto PATH.
- **No `--chrome-binary`/`--chrome-args` escape hatch on `browser start`**, and Chrome's stderr is discarded (`exec.Command` without stdout/stderr wiring), so a Chrome that can't start (root container → needs `--no-sandbox`) yields only `chrome did not become ready: timed out waiting for CDP` with zero diagnostics. Had to launch Chrome manually to discover the sandbox error. (The CfT 151 binary additionally hung headless in this container; Chromium 141 worked — environmental, but the CLI gave no way to see or fix either problem.)
- Errors themselves were loud (exit 1) — the failures were honest, just undiagnosable and mis-remedied by the docs.
- **Time to first useful output:** 2.5 s to a working CLI; **~3.5 min** from `browser start` to the first successful annotated snapshot of Plane, nearly all of it consumed by the two defects above. On a machine with a PATH-visible Chrome this would have been ~30 s.

## Phase 3 — Generate (author a corpus against Plane)

Followed the `sightmap-authoring` skill as an agent would: probe selectors → write YAML → snapshot → iterate. Full command traces are reproducible from the corpus in `.sightmap/`.

Result: 6 files, 5 views (LoginPage, WorkspaceHome, ProjectWorkItems, WorkItemDetail, ProjectCycles), 13 components, 4 documented API requests, 21 memory entries. `validate` clean, 1 advisory lint warning, captures for all 5 views.

What the loop got right (verified live):

- The **coverage ratchet works**: naming `WorkItemRow` + sidebar/header components took the issues page from 77/77 orphaned to 336 interactive · 82 % T2 · 31 orphaned, and the `Unlabeled clusters` selector hints were correct and usable.
- **Properties are the killer feature.** `key` via `transform: 'match:(FALCON-\d+)'`, `title` via a `p` sub-selector, `state` via a state-name alternation turned an anonymous `link > group` row soup into `[WorkItemRow key="FALCON-3" state="Backlog" title="Payment webhook retries…"]`. Work-item titles are **absent from the bare AX tree**, so this is information an agent otherwise cannot see without screenshots.
- `sel-probe` caught two of my bad selectors before they entered YAML (child scoping caught a third after).

What it got wrong or missed, and what a human must hand-edit:

1. **Capture sets are keyed by YAML file basename, not view name.** Docs say `snapshots/<view>/`. Two views in one file silently share one capture set, and `report` then attributes the first view's route and stats to the second (ProjectCycles displayed route `/*` with WorkspaceHome's numbers). Silent reporting corruption; fixed only by adopting one-view-per-file.
2. **Only view-level memory is surfaced.** File-level memory (my SPA-hydration and Vite-compile warnings, deliberately placed at file root per the spec's "applies whenever any definition from that file is active") never appears in any snapshot output; component memory appears only in `--json`. Practical authoring rule the docs don't state: anything an agent must see has to live on the view.
3. **Discovery tooling assumes test-id discipline.** Plane has zero `data-testid`/`data-component` anywhere; `sightmap suggest` returned "No candidate selectors found" — a no-op on this entire codebase. The only reliable app-provided hooks were PostHog analytics attributes (`data-ph-element`, 6 live instances), which no doc mentions as a selector source.
4. **The 0-orphan exit bar is unreachable on a hookless tailwind app.** Text-only controls (`button "Add work item"`, avatar buttons, ~30 icon buttons per view) have no CSS-addressable identity (no `:contains()` in CSS, sibling combinators unsupported). Final state: 31–94 orphans on 4 of 5 views, exhaustion documented in memory entries per the skill's own T2-triage rule. Closing the gap requires editing the app's source — real work the one-command marketing framing hides.
5. The overlay extension **mutates the page DOM** (`data-sightmap-id` attributes on elements, visible in `sel-probe` output) — observation is not passive, which matters for apps that react to attribute mutation and for anyone diffing DOM.
6. Authoring is **hand work with verification tooling, not generation**: ~16 minutes of interactive loop for 5 views, every selector found by reading the DOM myself. The site's "agents record what they learn" framing is accurate; anything suggesting automatic mapping is not.

Incidental: the enriched snapshots immediately surfaced two real Plane bugs (raw i18n keys leaking into `aria_labels.app_sidebar.*` aria-labels; a React hydration error on route load) — decent evidence that the observability layer has value beyond the map itself.

## Phase 4 — Consume (A/B, fresh contexts)

Four fresh agent contexts, same rules (sightmap CLI only, no app source, no direct API; mutations via real UI only). "Without" runs executed from a directory whose `.sightmap/` contained only the session file — bare AX trees, no component queries. App state reset between state-task runs.

**Task N (navigational):** find FALCON-5, report exact title + state from its detail page.
**Task S (semantic/state):** identify "the bug about payment webhooks" (never named in the prompt), move it to In Progress via the UI, verify it stuck.

| Run              | Commands | Tool uses | Tokens     | Wall time | Wrong turns | Outcome |
| ---------------- | -------- | --------- | ---------- | --------- | ----------- | ------- |
| N without corpus | 18       | 15        | 44,473     | 129 s     | 4           | success |
| N with corpus    | **6**    | 10        | **36,419** | **51 s**  | **1**       | success |
| S without corpus | 43       | 39        | 56,043     | 380 s     | 6 clusters  | success |
| S with corpus    | **25**   | 28        | **51,979** | **263 s** | 4 clusters  | success |

Deltas: nav task −67 % commands, −60 % time, −18 % tokens, wrong turns 4→1. State task −42 % commands, −31 % time, −7 % tokens, 6→4 wrong-turn clusters. **Success rate 4/4 in both conditions — the corpus buys efficiency, not capability, on these tasks.**

Where the value came from (with-corpus agents' own logs): the corpus's route pattern + `document.title` memory collapsed navigation to a direct URL; row **properties** made the semantic find instant (`snapshot | grep` showed FALCON-3's title in the tree), while the no-corpus agent needed screenshots plus `sel-probe --full` to learn which item was the webhook bug, having discovered titles are simply not in the bare tree.

Where the corpus did **not** help — the honest half:

- **Interaction physics dominated the state change in both conditions.** Both S runs fought the same fights: taking a `snapshot` **closes an open dropdown/popover** (the observe step destroys transient UI state — a major undocumented consumption gotcha), so both agents concluded their click had failed, re-clicked, and finally selected the option by raw coordinates.
- **Two of my memory entries were wrong, and wrong memory actively misleads.** "Clicking a WorkItemRow triggers SPA navigation" — it doesn't (the click lands without navigating; both conditions fell back to URL construction), and the with-corpus agent burned 3 commands trusting it. "State options are a headlessui listbox" — it's a combobox; the agent's `[role=listbox]` probe returned empty and it explicitly called out the corpus as the source of the error. The format has no mechanism to verify or age memory claims; a checked-in wrong sentence is authoritative-looking forever.
- Undocumented `wait-for --timeout-ms` cost turns in 3 of 4 runs; `scroll` silently no-ops on Plane's virtualized list while reporting success.

## What I'd fix first, as a ranked punch list

1. **Linux `FindChrome` must check `InstalledCfTPath()`** (parity with macOS) — the documented install flow is broken on the OS most CI/containers run. Add `--chrome-binary`/`--chrome-args`, and surface Chrome's stderr on CDP timeout.
2. **Remove `sightmap iterate` from the landing page** (or ship it). A nonexistent hero command is the fastest possible credibility loss for a skeptical evaluator.
3. **Close the schema↔CLI conformance gap**: add `match:` to the schema's transform enum (or pattern), and make `validate` enforce `version: 1` (currently unchecked entirely).
4. **Key capture sets by view name, not file basename** (or document the real rule and make `report` per-view stats correct for multi-view files).
5. **Warn on staleness in plain `snapshot`** — a defined component with 0 matches should be visible in the default read path, not only under `--coverage`.
6. **Document `wait-for --timeout-ms`**, the snapshot-closes-popovers behavior, and the DOM mutation (`data-sightmap-id`) — all three cost real agent turns in testing.
7. Surface file-level and component-level memory somewhere in the text output, or change the spec to match the implementation; add a staleness/verification story for memory entries (wrong memory is worse than no memory).
8. Detect multiple `.sightmap/` directories between CWD and repo root and warn.

## Bottom line

The value proposition survives contact with a real app, with one big asterisk. For _reading_ and _navigating_ a live SPA, the corpus measurably and sometimes dramatically reduces agent work, because properties and memory inject exactly the information the accessibility tree lacks — the nav-task delta (3× fewer commands, 2.5× faster) is not subtle, and it was delivered by a corpus authored in one 16-minute session. For _acting_ on the app, the delta shrinks toward zero: interaction is bottlenecked by UI physics the map cannot capture, and the format happily stores wrong lore that makes agents worse. The engineering quality of the failure modes is genuinely above average (loud, specific, usually with the right remedy in the message) — which makes the places it is silent (stale maps on the default path, corpus ambiguity, version checking, the schema drift) stand out as the work most worth doing before 1.0.
